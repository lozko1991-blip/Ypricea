# AI Rules & Guidelines for UTRADE Platform

Цей файл містить суворі інструкції для будь-якого ШІ (AI), який взаємодіє з цим кодом. **Завжди читайте цей файл перед початком внесення будь-яких архітектурних чи кодових змін.**

## 1. Стек технологій
- **Frontend:** React + Vite + TypeScript.
- **Styling:** Tailwind CSS + Shadcn UI (використовується vanilla CSS у `frontend/src/index.css` для кастомних токенів).
- **Backend/Data Parsing:** `process.mjs` (чистий Node.js), який викачує XML, розбирає його і кладе JSON в `frontend/public/data`.
- **Авторизація:** Supabase (`@supabase/supabase-js`).
- **Деплой:** GitHub Actions (`.github/workflows/update.yml`) -> GitHub Pages.

## 2. Суворі заборони
- **НЕ ЗМІНЮВАТИ** логіку генерації XML-каталогу (`process.mjs`) без попереднього аналізу того, як це вплине на React-компоненти, які очікують певний формат `index.json`.
- **НЕ ПИСАТИ** дані безпосередньо в директорію `frontend/dist`. Ця директорія генерується автоматично за допомогою команди `npm run build`.
- **НЕ ЛАМАТИ** існуючі імпорти компонентів Shadcn.
- **НЕ ПОРУШУВАТИ** дизайн-систему (premium look & feel, мікро-анімації, плавні градієнти). Усі компоненти мають виглядати сучасно і дорого.

## 3. Правила написання коду (Coding Standards)
- **Компоненти:** Тільки функціональні компоненти React з TypeScript. Назви файлів — `PascalCase.tsx` (напр., `ProductCard.tsx`).
- **Хуки та Утиліти:** Назви файлів — `camelCase.ts`.
- **UI Елементи:** ЗАВЖДИ пріоритетно використовуйте готові компоненти Shadcn UI (з папки `components/ui`). Якщо компонента немає — створіть його за допомогою CLI Shadcn або використовуйте Tailwind. Не пишіть "костильний" CSS.
- **Іконки:** Використовуйте тільки `lucide-react`. Жодних сторонніх SVG, якщо є аналог в Lucide.
- **Робота з даними (Supabase):** Завжди обробляйте 3 стани: `loading`, `error`, `success`. Використовуйте `try/catch` блоки для всіх асинхронних запитів.

## 4. Правила внесення змін (Workflow)
1. **Аналіз:** Прочитайте `ARCHITECTURE.md`, щоб зрозуміти, з яким шаром ви зараз працюєте (Парсер чи Фронтенд).
2. **Розробка:** Робіть правки локально (використовуючи `npm run dev` у папці `frontend`).
3. **Перевірка:** Перед завершенням завдання ви **ЗОБОВ'ЯЗАНІ** запустити `npm run build` у папці `frontend`, щоб переконатися, що TypeScript не має помилок.
4. **Логування:** Після УСПІШНОГО завершення серії правок, додайте детальний запис у `CHANGELOG.md`.

## 5. Безпека
- Усі змінні середовища для фронтенду повинні починатися на `VITE_` (наприклад, `VITE_SUPABASE_URL`).
- Жодних секретних ключів не має бути жорстко закодовано.
- Зміни в базі даних (RLS політики) мають бути задокументовані.
